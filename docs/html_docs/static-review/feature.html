What it is

After a coding session is captured, samskara reviews it and records what kind of session it was: did the work land, how much did the agent fight, and what should be learned from it. This page covers the static review — the deterministic analyzer named heuristic-v1, which is the only analyzer that exists today. It counts what the transcript shows (turn boundaries, tool results, edit timing) and never reads prose, so the same session always reviews the same way and no API key is ever required. Its output is a review row plus candidate lessons that wait for a human to accept or reject them; it is deliberately not a summary of what the session said.

An AI review is a planned, distinct thing: a second analyzer with its own name that implements the same SessionAnalyzer interface and would read the conversation with an LLM. It does not exist yet, and the heuristic stays the floor so the feature never depends on one. Every review row names its analyzer, so a verdict always says which kind produced it.

The flow end to end

Seven stages, trigger to visible result. A reader who stops here still knows how the feature works.

  1. Trigger. A review starts when someone calls POST /api/sessions/:id/review or runs samskara review. Both paths end in the same server function, reviewAndPersist. Nothing triggers a review on its own yet.
  2. Load. The server loads the session with getDetail, the same call the web UI’s session page uses — so a review sees exactly the rows a reader sees, and a user who cannot read a session cannot review it.
  3. Project. The stored messages map into a small neutral event vocabulary: turn, userMessage, toolCall, toolResult, edit, compaction, commit, pullRequest, tokens. Tool names join by callId, because results carry no name. Text survives only for user messages; the review never reads what anybody said, only when and in what order things happened.
  4. Analyze. HeuristicSessionAnalyzer folds the event stream into signals, then classifies friction and outcome from those signals.
  5. Extract. LearningExtractor walks the same signals into candidate lessons, each for an agent audience or a human audience, each fingerprinted for deduplication.
  6. Persist. The review upserts into sessionReviews, unique on (sessionId, analyzer); each candidate upserts into learnings by fingerprint as candidate, so re-reviewing a session does not duplicate rows.
  7. Surface. The /learnings web page lists candidates per project with Accept / Reject / Retire (human-check-only, editor-gated), and samskara learn --write exports accepted lessons into the repo’s .harness/knowledge/.

The data shape

The event vocabulary is the smallest honest unit the review speaks internally. Signals are its counted version: turns, aborted turns, user prompts, tool calls, tool failures and rate, error loops, edits per path, compactions, prompts-after-failures, rapid re-prompts, commits, pull requests, and four token totals.

Input vocabularies are enforced by zod schemas at ingest. Two projection rules collapse them into review states: a turn whose status is unknown reviews as completed (only aborted counts as aborted), and a user message with isMeta set is ignored as a harness injection, not a human prompt.

legal combinations

Outcome and friction are independent — all twelve pairs can exist, and shipped with high friction is a real, visible state. Within outcome itself, shipped and aborted are mutually exclusive by construction: aborted requires zero commits and shipped requires at least one commit or pull request, so no session can be both. productive and struggled differ only by friction — high friction with nothing landed is struggled.

lesson lifecycle

Lessons are born candidate from any review, and only a project editor (or owner/admin) can move them, via PATCH /api/learnings/:id/status. The intended transitions: candidate → accepted (the Accept button), candidate → superseded (Reject), accepted → superseded (Retire — the UI labels the state “Retired”), and superseded → candidate (a “Back to candidate” button on retired rows). The server validates the value and the editor’s right to set it, not the transition. Nothing but a human moves a lesson to accepted, ever.

lesson categories — the extractor’s fixed taxonomy

tool-retry (a tool kept failing before succeeding), rework (the same file edited many times), supervision (prompts arriving while failures piled up), prompt-shape, task-shape, context-hygiene (human-audience lessons about how the work was asked for).

Decision rules, with their real thresholds

friction — answered first

high if any error loop exists (3 or more consecutive failures of the same tool), or the tool failure rate exceeds 0.25, or 2 or more prompts arrived while failures were piling up — the human correcting course. moderate if the failure rate exceeds 0.10, or any turn was aborted. Otherwise none.

outcome — did the work land

aborted when the final turn aborted and zero commits. shipped when at least one commit or pull request exists, whatever the friction was — a high-friction shipped session stays visible as shipped with high friction because both fields are reported side by side. struggled when friction was high with nothing landed. productive for everything else.

fingerprints

Lesson fingerprints are audience:category:subject, so the same lesson from different sessions converges on one row with an occurrence count instead of duplicating.

What is deliberately not there

“Shipped” cannot happen today, so every session is mislabeled.

The load step fetches the session’s commits and pull requests, and the projection step throws them away — it maps messages only, so landing evidence never reaches the analyzer. Every session is mislabeled productive or struggled. This is the top fix in the roadmap.

No automatic trigger: reviews run only when a person asks.

Both entry points are explicit — the HTTP route and the CLI command. The watcher never starts a review; the roadmap item is review-on-quiet, a sweep in the watcher’s existing ten-second cycle.

Subagent tracks are not separated from the main conversation.

A subagent’s task prompt counts as a human prompt, and interleaving across tracks makes re-reviews wobble. The stored rows already carry a track id; the projection ignores it.

Occurrence counts inflate on re-review, and fingerprints split across machines.

Reviewing the same session twice counts as seeing the lesson twice — the count should move only when a different session shows it. And lesson fingerprints use absolute file paths, so the same lesson on two machines is two lessons.

An LLM analyzer is planned as an option, not a requirement.

An AI review would implement the same SessionAnalyzer interface under its own name (an llm-* analyzer, distinct from heuristic-v1), behind the same tests; the heuristics stay the floor so the feature never requires an API key to work.

How to see it work by hand

bun packages/cli/src/index.ts review --recent 1
psql postgres://samskara:samskara@localhost:5433/samskara -c 'select "sessionId", outcome, friction, summary from "sessionReviews" order by "analyzedAt" desc limit 5'
psql postgres://samskara:samskara@localhost:5433/samskara -c 'select "audience", "category", status, "occurrenceCount" from learnings limit 10'

The review prints its verdict and summary; the queries show the persisted rows and any candidate lessons. Accepting a lesson is a button on http://localhost:8000/learnings.
