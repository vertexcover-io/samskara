Self-learning samskara

The pieces that turn recorded sessions into lessons are built and all their tests pass, but five audits found the loop cannot actually close yet: the part that decides whether a session's work landed never sees the commits, and the part that writes lessons into a repo would erase the lessons already there.

Where are we

What the mission is. Sessions are already recorded and searchable. The mission closes the circle: judge each session, turn the judgments into lessons, and deliver the lessons to two readers — the repo, for the next agent, and the person, told plainly.

What exists. A judge per session: outcome, friction, and the specifics (the same tool failing three times, a file edited four times, prompts sent into mounting errors). Server-side lesson storage, deduplicated per fingerprint. Two commands: samskara review and samskara learn --write.

Why it can't close yet. Five audits agree on the blockers listed below. The doc audits' rewrites are already in.

Two roadmaps, read together

Where they came from. Two independent agents produced roadmaps this session — one from the project understanding alone (GLM-5.3), one from auditing what exists (MiniMax-M3). The code-grounded one re-verified all 13 audit findings with file:line evidence: three fixed (#3 scoping, #5 acceptance surface, #12 deleted script), ten still broken — the four criticals stand exactly as this page lists them. Both files live in writeup/self-learning/roadmaps/ and agree on the shape of the finish line.

What the synthesis changes. The understanding-driven roadmap adds five capabilities the code does not have — capture of opencode sessions through the unwired plugin registry, semantic similar-session retrieval on the idle pgvector store, loop-efficacy measurement, automatic review on session quiet, and delivery of accepted lessons to the next agent's eyes. It also forces one re-ordering: opencode capture goes first. It depends on nothing, and without it the mission has no real data to learn from — this very repo's sessions are opencode sessions, invisible to samskara today.

Synthesized order. 1. opencode capture source (W6 + B's seam map: loosen the server's source literal, build the plugin against opencode's sqlite session store, wire the registry into the watcher). 2. Truthful reviews (W1 = audit fix 1, plus tracks/tokens). 3. Safe write-back (W2 = fixes 2 and 4). 4. Review on quiet (W3 = fix 6). 5. Human feedback surface, semantic retrieval, efficacy measurement (W5, W7, W8 — in that order, each unlocked by the ones before it).

The loop now watches itself

Samskara is running on this repo. The server and web UI are live (API :3000, web :8000, local Postgres on :5433), the CLI is paired, and capture is enabled for this folder. The opencode capture source landed the same day: a plugin now reads opencode's own session database, and this repo's sessions — every one of them opencode — flow into the project vertexcover-io-samskara alongside any Claude sessions. The loop finally has real data to learn from; what follows below is making its judgments truthful.

What needs the owner

Nothing right now. The one open decision was settled: lessons promote by human check only — nothing accepts itself, ever. The curation page described below is that check. An LLM-backed judge later would need an API-key ruling; the heuristic one needs nothing.

Ruled, and built

Lessons promote by human check only — the owner ruled out any threshold that accepts by itself. The surface for that check now exists: a Lessons page in the web UI. It lists one row per lesson per project — who it is for (agents or humans), how many sessions showed it, the evidence pointers — with Accept and Reject buttons on candidates, and Retire on accepted ones. Only someone who can edit the project can press them; anyone who can merely read the project can read the lessons but not change their status. A second view on the same page, "common across projects", groups the same lesson appearing in two or more projects into one row with the project names listed — the tool-shaped lessons that are not really about any one project. It carries no buttons on purpose: a shared lesson is accepted or retired in each project's own view, by the people who own that project.

What is broken, worst first

  • The verdict "shipped" can never happen. The judge decides "shipped" when it sees a commit or a pull request, but nothing ever tells it about commits — the code that loads a session for review fetches its commits and pull requests and then throws them away. So every session that landed work is mislabeled, and every lesson built on top of that verdict stands on sand.
    packages/core/src/review/events.ts · services/review.ts:32
  • Writing lessons into a repo erases the lessons already there. This repo has four lessons written by hand before this mission. The write command regenerates the index file listing only what came from the server — and since nothing can be accepted yet (see the decision above), the first real run would write an empty index. The four files would still exist but nothing would list them, which is the same as losing them.
    packages/cli/src/commands/learn.ts:131 · .harness/knowledge/INDEX.md
  • Anyone paired with the server can read and re-rank any project's lessons. Every other part of the server checks that the asking user can see the project; the lessons list and its edit route check nothing.
    routes/reviews.ts:41-60
  • --project by name is silently ignored. The command only forwards a project when the value looks like a UUID. Given a name, it quietly fetches every project's lessons and writes them all into whatever repo you're standing in. The help text promises names work.
    learn.ts:57 · index.ts:130
  • Nothing ever reviews a session by itself. Capture runs automatically for everyone; judging and writing back are two commands somebody has to remember. The audits recommend the reviewer ride the watcher's existing ten-second loop — when a session's transcript has gone quiet, review it then.
    watcher/index.ts:152
  • Subagent work pollutes the judgment. A subagent's task prompt looks like a human prompt to the judge, and subagent and main lines interleave in no fixed order, so re-reviewing the same session can change the answer.
    services/review.ts:32 · schema.ts:227
  • "Seen 5 times" would be a lie. Reviewing the same session twice counts as seeing the lesson twice. The count should move only when a different session shows the same lesson.
  • Lesson titles can leak your username. File paths in lessons are absolute, taken straight from the agent's tool calls, so /Users/<you>/… lands in committed files — and the same file on two machines counts as two different lessons.

What does done look like

  • The foundation exists: the audit and writing skills are in the repo, the playbooks including the tone guide are in docs/playbook/, and the project-understanding doc says why the repo exists — the doc audits graded it and their corrections are in.
  • The whole dev stack now runs on this machine without Docker: one script starts a local Postgres on the port the compose file used, and the server's tests make themselves a throwaway database on it.
  • The judge exists and its tests say what it judges; the server stores reviews and lessons and its tests run against a real database; the two commands exist with tests. What is missing is not more machinery — it is the five fixes above before any of it is trusted with real sessions.
  • Not yet done, and it gates everything: one real session from this repo reviewed end to end, at least one lesson accepted, written back, and the hand-written index still intact afterwards. The writeup page comes after that closes.
